# ADR-0010: SQL on PostgreSQL with executable tests

- Status: Accepted, 2026-10-28

## 1 — Problem

The brief asks for two queries with schema and screenshots, and allows "a local database or an online SQL compiler". How do we
make the SQL deliverable verifiable rather than a picture, and how do we handle the wording ambiguities?

## 3 — Options

### A. Online SQL compiler plus screenshots

- First-order: exactly what the brief allows; fastest.
- Second-order: nothing is re-runnable; a screenshot can drift from the query text; the reviewer must trust the image.

### B. SQLite in-process (zero infrastructure)

- First-order: runs anywhere, tests need no server.
- Second-order: interval arithmetic and timestamps differ from the engines a company actually runs, so the queries would be
  written for a dialect nobody uses in production; it reads as a toy.

### C. PostgreSQL: schema + documented seed + queries as files, psql outputs and rendered screenshots, and Cucumber scenarios that
execute the same `.sql` files and assert exact rows; `docker-compose.yml` and a CI service container for reproducibility

- First-order: a database is required (Docker or local), and seed design takes real effort (every positive, decoy and boundary
  row is labelled with the rule it proves).
- Second-order: the evidence is regenerated by a command, not by hand; boundary semantics are enforced by tests (mutation checks
  showed that making either bound exclusive fails the suite); the same files serve humans and machines so they cannot drift.

## 1 — Decision

**Option C.** Interpretations recorded in `sql/README.md` and the query comments: the 24-hour window is directional (the return
follows the original) and inclusive, with simultaneous legs reported once using the lower transaction id as the original (a
review finding: the first version's strict `>` dropped them); the 10 % tolerance is relative to the original amount and
inclusive; "consecutive matches" defaults to consecutive innings the player batted in, with the team-fixture reading provided as
a second query and a seed player who separates the two. Revisit if the data source becomes a real ledger; then indexes and
partitioning, not semantics, are the next questions.
